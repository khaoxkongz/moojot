ผลตรวจจาก codebase ณ 1 ตุลาคม 2569 สำหรับ [ตรวจช่องว่างข้อมูลและ API ที่ดีไซน์ใหม่ต้องใช้](../issues/07-data-api-coverage.md) ใช้ [README ของ handoff](/Users/computer/Downloads/design_handoff_moojot_app/README.md) และ [ต้นแบบ](</Users/computer/Downloads/design_handoff_moojot_app/Moojot Home.dc.html>) เป็นแหล่งข้อกำหนด ครอบคลุมหน้าจอและ flow หลักทั้งหมด ผลนี้เป็นหลักฐานจาก source ไม่ใช่ผลตรวจแอปโฉมใหม่บนอุปกรณ์จริง

## ขอบเขตที่ตัดสินไว้แล้ว

อ่านคำตอบของ [กำหนดแพลตฟอร์มและวิธีทดลองแอปโฉมใหม่](../issues/01-device-validation.md#answer), [กำหนดความหมายของบัญชี บัตร และวันเวลาของรายการ](../issues/02-finance-data-model.md#answer), [กำหนดขอบเขตการเอากลับคืนหลังลบ](../issues/03-delete-undo.md#answer) และ [กำหนดการอ่านสลิปเมื่อเปลี่ยนหน้าหรือพักแอป](../issues/04-slip-reading-lifecycle.md#answer) เมื่อวางสัญญาข้อมูล ห้ามนำข้อมูลตัวอย่าง KTC 4821, เวลา 12:00/00:05 หรือวันที่ TODAY ในต้นแบบมาเป็นข้อมูลจริงของผู้ใช้

ตารางแยกสามกรณี: **ใช้ฐานเดิมได้** คือข้อมูลและ operation มีแล้วแต่หน้าจอยังต้องปรับ; **ปรับฝั่งแอป** คือทำจาก operation เดิมได้; **ปรับข้อมูล/สัญญา** คือเจ้าของข้อมูลหรือเงื่อนไขเดิมยังให้ผลตามดีไซน์ไม่ได้ ทั้งสามกรณีอาจอยู่ในหน้าจอเดียวกัน การพบช่องว่างไม่ได้แปลว่าต้องเพิ่ม endpoint ใหม่เสมอ

## ส่วนที่กระทบแผนมากที่สุด

1. รายการบัญชีมี soft delete/restore อยู่แล้ว แต่งบ กฎ หมวด และแท็กยังไม่มีการคืน identity และความสัมพันธ์ครบ การลบงบตามหมวด/แท็กมีอยู่แล้ว; ช่องว่างหลักคือ undo
2. กฎจดซ้ำไม่มีข้อมูลบัตร และการเปลี่ยนวันจดซ้ำอาจสร้างรายการย้อนหลังเพิ่ม เพราะ generator ย้อนตั้งแต่ startsOn ด้วยกฎที่แก้แล้ว ต้องให้การแก้มีผลครั้งถัดไปตาม handoff
3. ระบบอ่านสลิป บันทึก และกันซ้ำเดิมใช้ต่อได้ แต่ต้องมีข้อมูลแถวผลอ่าน งานค้าง การลองรูปที่เลือก และการจดเองจากรูปที่ยังไม่สำเร็จ
4. ข้อมูลสลิปปัจจุบันไม่มีธนาคาร บัตร คู่โอน และเวลาทำรายการจริงครบตามหน้าจอ ใช้ createdAt เป็นเวลาบันทึกได้ แต่ใช้แทนเวลาในสลิปไม่ได้
5. ค้นหาทุกเดือนใช้ listTransactions ที่ไม่ส่งขอบเขตวันและแบ่งหน้าได้อยู่แล้ว ส่วนการจับจำนวนเงินยังขาด ต้องไม่เรียกผลหน้าเดียวว่าเป็นผลทั้งหมด
6. Better Auth ที่ติดตั้งคืน INVALID_EMAIL_OR_PASSWORD ทั้งกรณีไม่พบอีเมลและรหัสผ่านผิด จึงต้องกำหนดสัญญาให้ข้อมูลเพียงพอก่อนแสดงข้อความสองแบบตาม handoff ไม่เดาจาก error เดียว

## งาน UI และ state ที่ไม่ต้องเพิ่ม API โดยตัวมันเอง

สี ฟอนต์ Regular/ตัวเลขระบบ ขนาดระยะ radius/shadow, safe areas, ขนาดปุ่ม, motion, keypad state, draft compare, period offset, wallet selection, toast, sheet stacking, FAB และ navigation เป็นงานฝั่งแอป ใช้ฐาน [typography](../../../apps/native/components/ui/typography.tsx), [fonts](../../../apps/native/constants/fonts.ts), [theme](../../../apps/native/constants/theme.ts), [stack](<../../../apps/native/app/(app)/_layout.tsx>) และ [tab layout](<../../../apps/native/app/(app)/(tabs)/_layout.tsx>) ก่อนวาง component ร่วม

แบบข้อมูลหลัก FinanceTransaction/Category/Tag/Budget/RecurringRule/Setting มีอยู่แล้วใน [finance.prisma](../../../packages/db/prisma/schema/finance.prisma) `wallet` ในต้นแบบเป็นตัวเลือกสำหรับ UI ไม่พิสูจน์ว่าต้องรื้อเป็น wallet entity ใหม่ โดยเฉพาะเมื่อรอบนี้รวมรายการตามธนาคาร

การเข้าสู่ระบบของบัญชีที่ onboarding ยังไม่จบให้วางเส้นทางต่อจาก [guard เดิม](../../../apps/native/app/_layout.tsx) เป็นข้อเสนอทางเทคนิคใน spec ไม่ถือข้อความย่อ signin→Home ว่าอนุญาตข้ามขั้นที่ยังไม่เสร็จ ต้องรายงานข้อจำกัดหาก flow ใหม่ทำตามคำสัญญาไม่ได้

Handoff ระบุ `statement` เป็น source ของข้อมูล แต่ไม่ได้เพิ่ม flow อัปโหลด statement/PDF และฟีเจอร์ที่บอกว่าจะทำรอบถัดไปอยู่นอกขอบเขต ไม่เปิดงานใหม่จาก enum หรือข้อความเร็ว ๆ นี้

## คำถามผลิตภัณฑ์ที่ต้องคุยต่อ

- [กำหนดผลเมื่อเปิดจดซ้ำหลังหยุดไว้](../issues/09-recurring-resume.md#answer) ตัดสินใจแล้ว: ข้ามวันครบกำหนดในช่วงที่กดหยุด และเริ่มครั้งถัดไปเมื่อเปิดกลับมา ต้องปรับ generator เดิมที่อาจจดย้อนช่วงหยุด
- [กำหนดวิธีระบุบัตรที่ยังไม่เคยจดรายการ](../issues/10-first-credit-card.md): ต้นแบบมีบัตรตัวอย่างพร้อมอยู่แล้ว ส่วนผู้ใช้จริงต้องมีทางให้รู้ชื่อและเลขท้ายครั้งแรก

การเลือก engine เก็บงานค้าง วิธี restore รูปแบบ endpoint และการแบ่ง component เป็นการตัดสินใจทางวิศวกรรมจากข้อกำหนดที่ตกลงแล้ว ไม่ให้ผู้ใช้ตอบแทนการตรวจข้อเท็จจริง ข้อตกลงในตารางเป็น input สำหรับ spec ไม่ใช่สัญญาว่า implementation ปัจจุบันครบแล้ว

## หลักฐานตรวจรับที่ต้องใส่ใน spec

- ข้อมูลเกิน 1,000 รายการ: all-month search, counts/totals, usage counts และ card totals ต้องครบ
- การจับจำนวนเงินและชื่อธนาคารไทย รวม exact card name+last4 เมื่อมีหลายบัตร
- วันเริ่มเดือน 29–31, ขอบเขต Summary/งบ/แนวโน้ม และ spent เท่ากับวงเงินพอดี
- cascade delete+undo ครบ identity/references และรักษาการแก้ข้อมูลอื่น รวมความล้มเหลวและ conflict
- new-rule backfill, edit next-only, resume policy และ editor→rule ไม่จด original ซ้ำ
- งานสลิปหลัง restart/>30 วัน, permission/photo unavailable, incomplete ไม่ส่งซ้ำ, transient retry และ manual-vs-inflight dedupe
- CSV 10 columns, Thai BOM, wallet labels, known/unknown actual time และ client/server format ตรงกัน
- Auth error mapping กับ onboarding guard, loading/error/empty states และ keyboard/safe-area/layout บน iOS/Android

ชุดทดสอบเดิมที่ผ่านไม่ใช่หลักฐานว่าพฤติกรรมใหม่เหล่านี้ทำครบแล้ว ต้องเพิ่มการตรวจที่ตรงผลลัพธ์ใหม่ในงานลงมือทำ
